# リファクタリング計画

「バグが多い」の出どころと、壊さずに直していく順番。言語やフレームワークは変えない
（TypeScript + React のまま）。理由は最後に書く。

## いまの形（2026-11 時点）

| 項目 | 値 |
| --- | --- |
| ソース | 約 19,400 行（TypeScript / TSX） |
| いちばん大きいファイル | `src/lib/layout.ts` 1,707 行（配置計算）、`src/store.ts` 1,518 行（状態と 150 超の操作）、`src/components/PanelCanvas.tsx` 1,477 行（図とドラッグ・キー操作） |
| 自動テスト | **無かった**（`tests/` を 2026-11 に追加。単体 21 件・画面 5 件） |
| 型チェック | `strict` + `noUncheckedIndexedAccess` で通っている |

## バグが出る構造

1. **配置計算が 1 本の長い関数に集まっている。** `packAuto` は段への流し込み・座標置きの回避・
   あふれの次段送り・ダクトの位置決めを 1 つの関数で行い、「以前は〜だった」という直しが
   積み重なっている。1 か所の直しが別の経路を壊す。
2. **描画と操作が同じコンポーネントにある。** `PanelCanvas` はドラッグ（並べ替え・座標置き・
   吸い付き）、矢印キー、ダクト・レールの選択、ズーム、目盛り、側面の投影を 1 ファイルで持つ。
   操作の分岐（Shift の有無・段の有無・レールに乗っているか）が増えるほど、見落としが出る。
3. **ストアに業務ルールが混ざっている。** `nudgeDuct` のように、状態の更新と「どこまで動かせるか」の
   計算（レイアウトを丸ごと計算し直す）が同じ場所にある。
4. **直した動きを固定するテストが無かった。** 直したそばから、別の直しで戻る。

## 進め方（壊さない順番）

### 0. テストの土台（済）

- `npm test` — Vitest。配置・レール・冷却・CSV・DXF の純粋な計算。
- `npm run test:e2e` — Playwright。ビルド済み `release/panel-studio.html` を開いて、
  矢印キー・ドラッグ・レールの伸び縮み・吹き出しを操作する。
- **以後、バグを直すときは先にそのバグを再現するテストを足してから直す。**

### 1. 配置計算の分割（`src/lib/layout.ts`）

- `packAuto` を「段の枠（slots）を作る」「1 台を置く場所を探す」「ダクトを決める」「段を上へ詰める」の
  4 つに分け、それぞれを単体テストで固定する。
- 座標置きの扱い（`pinned` / `onRail`）を 1 か所に寄せる。いまは `autoLayout`・`pushRowsUp`・
  `computeRails`・`PanelCanvas` のそれぞれが「レールに乗っているか」を判定している。
- 期待する動きは既存の README の記述と、このテストで決める。**数値の答えが変わる変更はしない。**

### 2. 操作の切り出し（`src/components/PanelCanvas.tsx`）

- ドラッグの判定（並べ替え／空き場所へ座標置き／独立レールへ吸い付き／止め金具の密着）を
  `src/lib/drag.ts` のような純粋な関数にして、座標と配置を渡すと「何をするか」が返る形にする。
  画面を通さず単体テストで試せるようになる。
- 矢印キーの処理（機器・ダクト・レール）も同じく関数に出す。

### 3. ストアの分割（`src/store.ts`）

- 部品表・案件・レイアウト・設定の 4 つのスライスに分ける。操作の数が多いので、
  まず「レイアウト操作」（pin / moveItem / nudge 系）だけを別ファイルに出す。
- 「どこまで動かせるか」の計算（`nudgeDuct` の中身）は `layout.ts` 側へ移し、ストアは結果を書くだけにする。

### 4. そのほか

- `release/panel-studio.html` の生成をコミット前に必ず通す（`npm run build:single` → `npm run test:e2e`）。
- ダクト余白・レール手直し・冷却など「案件に残る設定」の形を `types.ts` の 1 か所に集め、
  新規作成で何を白紙にするか（`freshProjectProfile`）をテストで固定する。

## 言語・フレームワークを変えない理由

- バグの原因は上の 1〜4 で、言語の問題ではない。書き直しても同じ構造にすれば同じバグが出る。
- 配布形態（共有フォルダに HTML 1 ファイル、ダブルクリックで開く、サーバー無し）は
  ブラウザで動くものでしか満たせない。
- 19,000 行の書き直しは数か月の空白になり、その間に出る現場の要望に応えられない。
  分割とテストなら、毎回の変更と一緒に少しずつ進められる。
