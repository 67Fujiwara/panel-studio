# リファクタリング計画

「バグが多い」の出どころと、壊さずに直していく順番。言語やフレームワークは変えない
（TypeScript + React のまま）。理由は最後に書く。

## いまの形（2026-11 時点）

| 項目 | 値 |
| --- | --- |
| ソース | 約 19,400 行（TypeScript / TSX） |
| いちばん大きいファイル | `src/lib/layout.ts` 1,707 行（配置計算）、`src/store.ts` 1,518 行（状態と 150 超の操作）、`src/components/PanelCanvas.tsx` 1,477 行（図とドラッグ・キー操作） |
| 自動テスト | **無かった**（`tests/` を 2026-11 に追加。単体 21 件・画面 5 件） |
| 型チェック | `strict` + `noUncheckedIndexedAccess` で通っている |

## バグが出る構造

1. **配置計算が 1 本の長い関数に集まっている。** `packAuto` は段への流し込み・座標置きの回避・
   あふれの次段送り・ダクトの位置決めを 1 つの関数で行い、「以前は〜だった」という直しが
   積み重なっている。1 か所の直しが別の経路を壊す。
2. **描画と操作が同じコンポーネントにある。** `PanelCanvas` はドラッグ（並べ替え・座標置き・
   吸い付き）、矢印キー、ダクト・レールの選択、ズーム、目盛り、側面の投影を 1 ファイルで持つ。
   操作の分岐（Shift の有無・段の有無・レールに乗っているか）が増えるほど、見落としが出る。
3. **ストアに業務ルールが混ざっている。** `nudgeDuct` のように、状態の更新と「どこまで動かせるか」の
   計算（レイアウトを丸ごと計算し直す）が同じ場所にある。
4. **直した動きを固定するテストが無かった。** 直したそばから、別の直しで戻る。

## 進め方（壊さない順番）

### 0. テストの土台（済）

- `npm test` — Vitest。配置・レール・冷却・CSV・DXF の純粋な計算。
- `npm run test:e2e` — Playwright。ビルド済み `release/panel-studio.html` を開いて、
  矢印キー・ドラッグ・レールの伸び縮み・吹き出しを操作する。
- **以後、バグを直すときは先にそのバグを再現するテストを足してから直す。**

### 1. 配置計算の分割（済・2026-11）

`src/lib/layout.ts`（1,707 行）を `src/lib/layout/` に分けた。他のファイルからの import は変えていない。

| ファイル | 中身 |
| --- | --- |
| `constants.ts` | しきい値と固定値 |
| `types.ts` | `DeviceLookup`・`LayoutItem`・`Entry`・`Obstacle` など |
| `clearance.ts` | 離隔・寸法・段の余白・基準線の上下に要る高さ |
| `ducts.ts` | レイアウト規則、縦ダクトの帯、段の区画、equal モードの段割り |
| `pack.ts` | 流し込み。**`rowSlots`（枠を作る）→ `findSlot`（置き場所を探す）→ `resolveRows`（段とダクトを決める）** |
| `push.ts` | 段を上のダクトの手前まで詰める |
| `rails.ts` | DINレール（共通・独立・手直し） |
| `checks.ts` | 重なり・干渉・スロット・奥行きの検査 |
| `index.ts` | `autoLayout` と公開する名前 |

- 数値の答えは `tests/unit/layout.golden.test.ts`（10 シナリオのスナップショット）で分割前と同じことを確かめた。
- 3 手順それぞれの保証は `tests/unit/pack.test.ts` に書いた。
- 残り: 座標置きの扱い（`pinned` / `onRail`）はまだ `index.ts`・`push.ts`・`rails.ts`・`PanelCanvas` に
  散っている。次に `PanelCanvas` の操作を切り出すときに 1 か所へ寄せる。

### 2. 操作の切り出し（済・2026-11）

- `src/lib/layout/drag.ts` — ドラッグ 1 コマの判定 `decideDrag`（Shift の座標置き／止め金具の密着／
  独立レールへの吸い付き／空いた場所への座標置き／並べ替え）。ダクト避け・吸い付き・入れ込み先も
  それぞれ関数。`PanelCanvas` はポインタを面の座標に直して渡し、返った決定を書くだけ。
- `src/lib/layout/nudge.ts` — 矢印キーの判定。機器 `nudgeDevice`、横ダクト `planDuctNudge`
  （どこまで動かせるか・理由）、縦ダクト `planVertNudge`、レールの端 `planRailNudge`、
  図のダクトとキーの読み替え `ductKeyMove`。ストアの `nudgeDuct` は答えを書くだけになった。
- 座標置きの判定は `pinnedAt` / `snapToRowRail` / `isOnRowRail` の 1 か所に寄せた。
- テスト: `tests/unit/nudge.test.ts`、`drag.test.ts`、`interact.combo.test.ts`（人の手順どおりの組み合わせ）、
  `interact.fuzz.test.ts`（でたらめな順番で 60 手 × 5 種を繰り返しても崩れない不変条件）。
- 見つけて直したバグ: DIN 機器を 1mm 上下に動かすと独立レールになって段の共通レールを切り刻み、
  隣の機器のレールが消えていた。レールの帯に掛かる高さなら段のレールに吸い付かせ、帯の外ぎりぎりで
  掛かるものは隣のレールを削らず「レールが重なっている」と検査に出すようにした（`railOverlaps`）。

### 3. ストアの分割（`src/store.ts`）

- 部品表・案件・レイアウト・設定の 4 つのスライスに分ける。操作の数が多いので、
  まず「レイアウト操作」（pin / moveItem / nudge 系）だけを別ファイルに出す。
- 「どこまで動かせるか」の計算（`nudgeDuct` の中身）は `layout.ts` 側へ移し、ストアは結果を書くだけにする。

### 4. そのほか

- `release/panel-studio.html` の生成をコミット前に必ず通す（`npm run build:single` → `npm run test:e2e`）。
- ダクト余白・レール手直し・冷却など「案件に残る設定」の形を `types.ts` の 1 か所に集め、
  新規作成で何を白紙にするか（`freshProjectProfile`）をテストで固定する。

## 言語・フレームワークを変えない理由

- バグの原因は上の 1〜4 で、言語の問題ではない。書き直しても同じ構造にすれば同じバグが出る。
- 配布形態（共有フォルダに HTML 1 ファイル、ダブルクリックで開く、サーバー無し）は
  ブラウザで動くものでしか満たせない。
- 19,000 行の書き直しは数か月の空白になり、その間に出る現場の要望に応えられない。
  分割とテストなら、毎回の変更と一緒に少しずつ進められる。
