# 制御盤 自動配列 + BOM 自動化 Webアプリ — 仕様レビューと技術判断

対象仕様書: `vrain_panel_automation_spec.md`（Claude との相談メモ）
このドキュメントの目的: 仕様書を読んだうえでの **(A) 技術スタックの決定 / (B) 方針変更の提案 / (C) 未確定事項 / (D) 不明点 / (E) 設計方針 / (F) 差別化とロードマップ** の整理。

## 決定事項（確認済み）

| 項目 | 決定 | 影響 |
| --- | --- | --- |
| 技術スタック | **TypeScript + React + Vite / 100%ブラウザ動作・単一HTML配布** | サーバー不要。インストール不要で配布できる |
| CAD 環境 | **AutoCAD LT** | LT は COM/ActiveX 自動化に非対応 → **COM 連携は恒久的に対象外。DXF 書き出し一本** |
| 取り込み形式 | **DXF**（PDF は不採用） | 実寸 mm を直接読める。PDF は縮尺逆算で静かに誤る |
| v1 スコープ | **単一基板の壁掛キャビネット**（扉面機器・自立形・複数基板は対象外） | レイアウトモデルを 1 面に固定でき、最短で実物が出る |
| リポジトリ | **専用の新規リポジトリ**（他アプリとは完全に分離） | 構成・ビルド・配布を独立させる |

**この決定により Python は一切使いません。** 仕様書にあった Python + FastAPI + pywin32 の構成は、AutoCAD LT が COM 非対応であることが確定した時点で成立しないため、全面的に取り下げます。

## 1. 結論：技術スタックを決める

> 「使用する言語は決めちゃって」への回答。

### 決定

| 層 | 採用 | 理由 |
| --- | --- | --- |
| 言語 | **TypeScript** | 盤の寸法計算が中心のアプリ。mm / 個数 / 型式の取り違えを型で潰せる。JS のままだと確実に事故る |
| UI | **React 19 + Vite** | ドラッグ配置・リアルタイム再描画に必要な部品が揃っている。ビルドが速く、単一HTML化の実績がある |
| 盤面エディタ | **SVG（自前の pan/zoom・ドラッグ）** | 機器数はせいぜい数百。SVG なら実装が軽く、印刷・PDF 出力・拡大に強い。Canvas(konva) が要るのは数千要素からで、今回は不要 |
| 状態管理 | **Zustand + immer** | 盤エディタには Undo/Redo が必須。自前フックだと履歴管理がつらい |
| 保存 | **IndexedDB**（機器マスタ・DXF キャッシュ）<br>**File System Access API**（My設定ファイル） | localStorage は 5MB 前後で機器マスタ＋DXF に足りない。File System Access なら共有フォルダ上のファイルを直接読み書きできる（Chrome/Edge） |
| DXF 読み込み | `dxf-parser` + 自前レンダラ | 後述の「半自動取り込み」方式なら JS で十分 |
| DXF 書き出し | **自前ライター（DXF R12 ASCII）** | DXF の書き出しはテキスト生成。ライブラリを挟まないほうがレイヤ名・線種・ブロック名の社内規則に合わせやすい |
| BOM(Excel) | `exceljs` | 書式・列幅・罫線つきで出せる |
| BOM(CSV) | 自前 + `encoding-japanese` | 国内 ERP の **Shift-JIS(CP932)** 要求にブラウザだけで対応できる |
| 配布 | **単一 HTML ファイル**（`vite-plugin-singlefile`） | 共有フォルダに置いてダブルクリックで開ける。インストール不要＝「他の人に展開」の障壁が消える |

### 「Python + FastAPI + pywin32」から変更する理由

仕様書では Python ローカルサーバー + AutoCAD COM 連携が前提でしたが、**100% ブラウザ動作に変更します**。

1. **AutoCAD LT は COM/ActiveX 自動化に非対応（確定）。** 社内環境が LT である以上、pywin32 による COM 連携は**そもそも動きません**。仕様書の構成はこの一点で成立しなくなります。**DXF 書き出しなら AutoCAD / LT / BricsCAD いずれでも開ける**ので、こちらが唯一の現実解です。
2. **展開のしやすさ。** 目標に「ゆくゆくは他の人にも展開したい」がある。Python + ローカルサーバー方式は、配る相手ごとに Python・依存パッケージのインストールとポート設定が要る。「HTML 1ファイルを共有フォルダに置いてダブルクリック」なら障壁ゼロ。
3. **UI の作り込みが本体。** 「誰もが使いたがる直感的な UI」はドラッグ配置・スナップ・リアルタイム干渉表示が肝で、そこはフロントエンドの仕事。Python の UI フレームワークでは到達点が低い。
4. **DXF 書き出しに Python(ezdxf) は必須ではない。** 出力するのは矩形・線・円・テキスト・ブロック参照程度。TypeScript で十分書ける。

### DXF 書き出しで運用上足りる

「DXF を書き出して AutoCAD LT に挿入」で完結します。LT では COM も AutoLISP による自動化も当てにできないため、**アプリ側が完成した DXF を出し、人はそれを開く／挿入するだけ**という境界にします。この境界はむしろ設計上きれいで、CAD 側の環境差に一切依存しなくなります。

そのぶん **DXF の品質が製品品質そのもの**になります。レイヤ名・線種・文字スタイル・ブロック名を社内標準に合わせ込むことに実装コストを寄せます（→ 第4章で既存図面のサンプルを頂きたい理由）。

## 2. 仕様書からの方針変更・補強の提案（3点）

### 提案1: PDF ではなく **DXF を採用**（判断済み）

> 「PDF か DXF か、精度の高いほうを採用して」への回答。

**DXF を採用します。** 理由は精度の性質が違うからです。

| | DXF | PDF |
| --- | --- | --- |
| 座標 | 実寸(mm)がそのまま入っている | 紙上のポイント値。縮尺を逆算する必要があり、丸め誤差が乗る |
| 寸法の取得 | 図形の座標から直接 | 寸法線の数値をテキスト抽出 → 図形との対応付けが必要 |
| 失敗モード | 少ない | 縮尺推定ミス・OCR 誤読で **静かに間違った値が入る** |

制御盤は 1mm の取り違えが干渉になるので、「静かに間違う」PDF 経路は採用しません。
なお日東工業は商品情報サイト **N-TEC** で **DXF 形式**の 2D 図面データを配布しており（キャビネット・盤用パーツ・ブレーカ・端子台など）、無料のメンバー登録で入手できます。3D は STEP と 3D PDF が 2025 年から提供開始。**PDF はカタログの仕様表（質量・消費電力など）を人が読んでマスタに入れる用途**に限定するのが妥当です。

**⚠ ライセンス上の重要注意：** N-TEC の図面データは **無断の改変・転載・譲渡・販売が禁止**されています。したがって **DXF をアプリに同梱して配布してはいけません。** 「各自が N-TEC からダウンロード → アプリに読み込む」導線にし、アプリ側には**寸法値（数値）だけ**を持つ設計にします。数値そのものはカタログ記載の事実なので、この切り分けなら安全です。

### 提案2: **「盤マスタ」を主、DXF 取り込みは従** にする

DXF から全自動で盤情報を取るのは、思っているより難物です。メーカー図面は三面図・寸法線・表題欄・ハッチングが 1 ファイルに同居しており、「どの矩形が基板（取付板）か」を機械的に当てるのは不安定です。

そこで **半自動方式**を提案します。

1. DXF を読み込んでブラウザ上に描画する
2. アプリが候補（正面図で最大の閉じた矩形など）を**推定してハイライト**
3. 人が「これが基板」「これが扉開口」とクリックで確定（2点ピックでも可）
4. 確定した数値を **盤マスタに型式キーで保存** → **次回から同じ型式は全自動**

つまり DXF 取り込みは「マスタを育てるための入力補助」であって、毎回走る必須経路ではありません。これが一番早く・一番壊れません。

**DXF 読み込み時の実装上の注意（先に潰しておくべき点）**
- `$INSUNITS` を見て単位を判定（mm 前提で決め打ちしない）
- ブロック参照(INSERT)のネスト展開が必要。スケール・回転付き INSERT に注意
- 寸法(DIMENSION)・ハッチング・表題欄はレイヤで除外できることが多い
- 円弧(ARC)/ポリライン(LWPOLYLINE)のバルジを含むバウンディングボックス計算

### 提案3: **奥行き(Z)の入力項目を 2 つに分ける**

> 「制御盤背面から基板上面までの距離が正しくないので手動入力」への補強。

手入力にするのは賛成です。ただし**干渉判定に本当に必要なのは「基板上面から扉内面までの有効奥行き」**です。ここが足りないと、深形の機器やハンドル付きブレーカが扉に当たります。以下を入力項目にします。

```
盤外形奥行き D
├ 背面内側 → 基板上面 の距離 t   ← 手入力（ここが図面と合わない箇所）
├ 基板上面 → 扉内面 の有効奥行き H_eff  ← 自動計算 or 手入力
└ 扉裏の突出量（ハンドル・扉面機器）  ← 手入力
```

各機器の奥行き寸法と突出量（DIN レール分 7.5/15mm も加算）を足して `H_eff` と比較 → 超えたら警告。**これは「盤内レイアウト自動化」を名乗る他ツールでも意外と抜けている部分**で、実務価値が高いです。

8. 盤内温度上昇の計算や換気扇選定まで自動化したいか（IEC 60890 相当の簡易計算）

**技術的に検証が必要なこと（こちらで潰します）**

9. `dxf-parser` が N-TEC の実データを問題なく読めるか（**実ファイル 1 つで検証したい**）
10. 単一 HTML にしたときのファイルサイズ（exceljs を含めると数 MB になる可能性 → 遅延読み込みや軽量代替の検討）

### ERP 未定でも止まらないようにする

ERP が決まっていないことは**ブロッカーにしません。** CSV 出力を「列名・並び順・文字コード・区切り文字・囲み文字を **My設定ファイル側で定義する汎用エクスポータ**」として作ります。ERP が判明したら、コードを触らずマッピング定義を書くだけで対応できます。

## 5. 設計方針

### 5.1 データモデル（単一の情報源）

```ts
type MountType = 'din' | 'plate' | 'door';

type Device = {
  id: string;
  maker: string;          // 日東工業 / 三菱電機 / ...
  model: string;          // 型式（BOM のキー）
  name: string;
  category: 'breaker' | 'contactor' | 'relay' | 'plc' | 'terminal' | 'psu' | 'other';
  size: { w: number; h: number; d: number };   // mm
  mount: MountType[];                          // 対応する取付方式（複数可）
  mountHoles?: { x: number; y: number; dia: number }[];  // 直付け時のケガキ座標
  clearance?: { top: number; bottom: number; left: number; right: number }; // メーカー指定の最小離隔
  heatW?: number;         // 消費電力/発熱
  doorProjection?: number;// 扉側への突出量
  accessories?: { model: string; qtyPer: number }[]; // 付属で必ず要る部品
};
```

**ポイント**
- 機器マスタは **レイアウトと BOM の両方が参照する唯一の情報源**（仕様書の方針どおり。ここは完全に同意）
- `clearance` を**機器ごとに持つ**のが重要。グローバル設定と機器個別値の **大きいほう** を採用する（メーカー指定が下回ってはいけない）
- `mount` を配列にすることで「DIN でも直付けでも付く機器」を表現し、案件ごとに選ばせる

### 5.2 レイアウトエンジン

**座標系**：基板左下を原点、X 右、Y 上、単位 mm。

**行(Row)モデル**：基板を水平ダクトで区切って複数の「機器行」を作り、各行に DIN レール or 直付ゾーンを 1 本置いて左から詰める。行幅が足りなければ次の行に折り返す。

**v1 では最適化アルゴリズムを入れません。** 決定論的な greedy 配置で十分です。実務で求められているのは「隙間なく詰める」ことではなく「主幹は左上」「端子台は最下段」といった**人間のルールどおりに並ぶ**ことだからです。2D ビンパッキングの最適解は、見た目が人間の常識から外れて逆に使われなくなります。

**安定配置（差別化ポイント）**：機器を 1 台追加したときに**全体が組み替わらない**こと。既に座標が決まっている機器は固定し、新規機器だけ空きに入れる。全再計算は「再配置」ボタンを押したときだけ。実務ではこれが効きます。

### 5.3 ダクトレイアウト（プリセット）

> 「好みが分かれそうだから何パターンか用意して」への回答。

| # | パターン | 内容 | 向いている盤 |
| --- | --- | --- | --- |
| 1 | **横ダクト段組み** | 上から ダクト / 機器行 / ダクト / 機器行 … | 最も一般的。汎用制御盤 |
| 2 | **縦ダクト両サイド** | 左右に縦ダクト、中央に機器を横並び | 機器が少なく横長の盤 |
| 3 | **田の字（外周＋十字）** | 外周ダクト + 中央に縦横のダクト | 大型盤・ゾーン分けしたい場合 |
| 4 | **ゾーン分割（動力／制御）** | 上下または左右で動力/制御を分け、境界に縦ダクト | ノイズ分離が要る盤 |
| 5 | **端子台最下段専用** | 最下段を端子台列に固定、その上に横ダクト | 外部配線が多い盤 |
| 6 | **カスタム** | ダクト矩形を手で描く | 例外案件 |

各パターン共通のパラメータ：ダクト幅（40/50/60/80/100）、段数、段ピッチ（自動 or 固定）、上下左右の余白、DIN レール高さ。

**追加提案：ダクトサイズの自動推奨。** 各行を通る電線の本数と断面積から必要ダクト断面積を計算し、占積率（一般に 40〜50% 以下が目安、※社内基準要確認）を満たすサイズを提案する。これは他のツールがあまりやっていない領域です。

### 5.4 クリアランス設定

> 「ダクトに対してクリアランスがどのくらい欲しいか入力する項目」への回答。1 個の数値では足りません。

以下を**個別に**設定できるようにします（すべて My設定ファイルに保存）。

- 機器 ⇔ ダクト（上／下／左／右を別々に）
- 機器 ⇔ 機器（同一行内／隣接行間）
- 機器 ⇔ 基板端
- 発熱機器の追加離隔
- 端子台の締付作業スペース
- 扉内面との奥行きクリアランス

**適用ルール：`実効クリアランス = max(グローバル設定, 機器個別の指定値)`**

**UI：数値を変えたら盤面図がその場で追従し、違反箇所が赤くハイライトされる**こと。これが「触っていて気持ちいい」の正体です。

### 5.5 取付方式（DIN レール / 直付け）

> 「機器ごとに設定したい」への回答。

- 機器ごとに `din` / `plate` を選択（マスタの `mount` が許す範囲で）
- **DIN レールそのものをレイアウト上のオブジェクトとして持つ** — 行ごとに 1 本、長さを持ち、BOM に「切断長 ◯mm × ◯本」として出る。エンドストッパも自動で付く
- DIN レール取付時は**実効奥行きにレール高さ（7.5 / 15mm）を加算**して干渉判定
- 直付け機器は**取付穴のケガキ座標を出力**（→ 基板加工図・日東工業キャビスタの穴加工指定に繋がる）
- 同一行に DIN と直付けを混在させない（制約として実装）

### 5.6 BOM

**BOM 自動化の本当の価値は「機器本体」ではなく「派生部品」です。** 手作業で一番漏れるのがここ。

自動で追加するもの：
- DIN レール（切断長 → 定尺からの必要本数と歩留り）
- エンドストッパ
- 配線ダクト（必要長 → 2m 定尺から本数算出、端材も表示）
- 取付ネジ・ナット・スペーサ（取付方式と機器数から）
- アース線・アースバー
- 機器の必須付属品（`accessories`）

出力は仕様書どおり 2 系統に分けます。
- **人の確認用**: `.xlsx`（exceljs、書式つき）
- **ERP 取込用**: `.csv`（文字コード・区切りを My設定で定義、Shift-JIS 対応）
- CSV は人が Excel で開いて編集しない運用（型式のゼロ落ち・指数表記化を防ぐ）

### 5.7 My設定ファイル

> 「ゆくゆくは他の人にも展開したいから My設定ファイルを作って」への回答。

単一 JSON（`*.vpanel.json`）に以下をまとめ、書き出し/読み込みできるようにします。

```jsonc
{
  "schemaVersion": 1,
  "profileName": "Vrain標準",
  "devices": [ /* よく使う機器セット・お気に入り構成 */ ],
  "clearance": { /* 5.4 の全項目 */ },
  "ductPresets": [ /* 5.3 のお気に入り */ ],
  "drawing": { "layers": {}, "textStyle": "", "blockNaming": "" },
  "bom": { "columns": [], "order": [], "encoding": "cp932", "delimiter": "," },
  "rules": { /* 主幹は左上、端子台は最下段 などの社内ルール */ }
}
```

- **`schemaVersion` を最初から入れる**こと。後からマイグレーションが書けます（ここを省くと必ず後悔します）
- 「書き出し / 読み込み」に加えて、**編集後に共有フォルダへ自動バックアップ**する導線を用意します（File System Access API でフォルダを一度許可すれば以降は自動）
- 展開フェーズでは「会社の標準プロファイル（読み取り専用）」＋「個人の上書き」の 2 層構造にすると運用が楽

## 6. 既存製品との差別化

> 「多分この感じの機能はすでに世の中にあるからそれを超えるものを作りたい」への回答。

**調べた結果、正面衝突する製品は実はありません。** 隣接する 2 つはこうです。

| 製品 | やっていること | 隙 |
| --- | --- | --- |
| **EPLAN Pro Panel** | 制御盤の 3D レイアウト、自動配線、板金加工図・部品表の自動生成 | **上流に EPLAN Electric P8 の回路図データが必要**。高価・重量級・導入に時間がかかる |
| **日東工業 CABISTA / スマートオーダーキャビネット** | キャビネット本体のカスタマイズ（穴加工・基板加工・扉組替）の Web 作図と見積 | **箱側だけ。盤内の機器レイアウトと BOM は対象外** |

つまり狙う位置は明確です。

> **回路図なしで、「機器リスト」と「盤型式」だけから盤内レイアウトと BOM を出す、軽量ツール。**

EPLAN の下、キャビスタの隣。ここは空いています。

**具体的に「超える」ための差別化ポイント（効く順）**

1. **安定配置** — 機器を 1 台足しても既存配置が壊れない（5.2）。実務で一番ストレスが減る
2. **奥行き干渉チェック** — 扉裏との干渉まで見る（提案3）。意外と抜けている
3. **派生部品の自動 BOM** — DIN レール切断長・ダクト定尺・ネジまで（5.6）。ここが手作業の温床
4. **リアルタイムのルール違反表示** — クリアランス・発熱・奥行きを触った瞬間に赤く出す（5.4）
5. **基板加工穴座標の出力** — キャビスタの穴加工指定に繋げられる
6. **学習コストゼロ** — HTML 1 ファイル、インストール不要、日本語、日東工業標準品にネイティブ対応
7. （v2）**盤サイズの逆引き提案** — 機器リストから必要な盤型式を推奨
8. （v2）**盤内温度上昇の簡易計算** — 総発熱から換気扇/クーラーの要否を判定

## 7. ロードマップ

**Phase 0 — 土台（動くものを最短で）**
- 専用リポジトリの作成、TypeScript + React + Vite セットアップ、単一HTMLビルドの確認
- 機器マスタのスキーマ確定、実案件の機器 20〜30 点を手入力
- 盤面の SVG 表示（基板 + グリッド + pan/zoom）

**Phase 1 — レイアウトの中核**
- ダクトプリセット 1〜2 パターン（横ダクト段組み優先）
- 機器の自動配置（greedy）+ ドラッグでの手動微調整 + スナップ
- クリアランス設定 UI とリアルタイム違反表示
- DIN / 直付けの切り替え
- **既存図面と突き合わせて精度検証**（仕様書の段階的アプローチどおり）

**Phase 2 — 出力**
- DXF 書き出し（レイヤ規則を社内標準に合わせる）
- BOM: xlsx + 汎用 CSV エクスポータ
- My設定ファイルの書き出し/読み込み

**Phase 3 — 育てる**
- DXF 半自動取り込み → 盤マスタの自動蓄積
- ダクトパターン残り、盤サイズ逆引き、発熱計算
- 基板加工穴座標の出力（キャビスタ連携を視野に）

各 Phase の終わりで単一 HTML をビルドして実案件で使ってみる、を必ず挟みます。**「自動仮配置 + 人が微調整」を第一段階のゴールにする**という仕様書の方針は正しいので、そこは変えません。
